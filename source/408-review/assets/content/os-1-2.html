操作系统能管理整台机器，靠的不是“权限大”，而是 CPU 提供的两种执行状态：用户态和内核态。模式位把“普通程序能做什么”和“内核能做什么”划开；中断、异常和陷入则是跨过这条边界的合法通道。理解这一节，后面进程切换、系统调用、缺页处理、I/O 中断才有共同的语言。

一、为什么 CPU 要分两种模式

假设一台机器只有一种执行状态：应用程序可以直接执行 I/O 指令、修改页表基址、关中断、改写中断向量。那么任何一个有 bug 或恶意的程序都可以：

  • 把别的进程的内存映射到自己的地址空间，读走密码；
  • 关掉时钟中断，永远占着 CPU；
  • 改写中断向量，让 I/O 完成时跳到自己指定的代码；
  • 直接对磁盘控制器发命令，绕过文件系统的权限检查。

所以“保护”不能只靠软件自觉，必须由硬件提供一条不可被普通程序绕过的边界。CPU 模式就是这条边界：把会改变全局机器状态、访问受保护资源的指令标记为特权指令，只在核心态允许执行；用户态执行特权指令会触发异常，而不是“悄悄执行”。

这也解释了为什么操作系统必须运行在内核态：它要管理页表、响应中断、控制设备、切换进程，这些操作天然是特权操作。但“内核态”不是内核的专利，而是 CPU 的一种状态；理解这一点，才能把“谁在运行”和“以什么权限运行”分开。

二、PSW 与模式位

程序状态字寄存器（PSW，Program Status Word）保存当前程序运行的状态信息。不同体系结构里它可能叫 PSW、FLAGS、EFLAGS、CPSR、RFLAGS 等，字段也不完全一样，但通常包含几类信息：

字段作用与本节的关系
条件码/标志位ZF、CF、OF、SF 等，记录上一条运算的结果特征条件转移、算术运算使用；属于程序可见状态
中断允许位控制 CPU 是否响应可屏蔽中断关中断/开中断是特权操作；影响中断响应
CPU 模式位标识当前是内核态还是用户态决定能否执行特权指令、访问受保护资源
优先级/其他控制位部分体系结构用于中断优先级、单步、对齐检查等因机器而异，考试按题目给出的定义

模式位是最关键的一位。常见约定是 0 表示内核态、1 表示用户态，但这不是跨体系结构的统一标准：x86 用 CPL（Current Privilege Level）0/3 表示最高/最低特权级，RISC-V 用 U/S/M 三种模式。408 题目如果明确给出“0 内核、1 用户”，就按题目；如果只问“模式位的作用”，答“标识 CPU 当前工作状态、控制特权指令执行”即可，不要死背某一种编码。

模式位不是普通寄存器里的一个“变量”，它属于受保护的处理器状态：用户程序不能直接用一条普通指令把它改成 0；只有硬件在响应中断/异常时，或内核执行特定的返回/切换指令时，才会改变它。PSW 本身也会在中断响应时被保存，在返回时被恢复；这正是“用户态程序被打断后还能正确继续”的原因。

三、用户态与内核态各自能做什么

用户态（目态）是应用程序运行的状态。它只能执行非特权指令，只能访问自己的地址空间，不能直接操作设备、修改页表、关中断或改变模式位。用户程序想让操作系统帮忙，必须通过系统调用发出请求。

内核态（核心态、管态、特权态）是操作系统内核和硬件事件处理程序运行的状态。它可以执行全部指令，访问全部物理内存和 I/O 空间，修改页表、中断向量、时钟和 PSW。内核态的权力更大，责任也更大：内核里一个越界写，可能直接破坏整台机器，而不是只让一个进程崩溃。

能力用户态内核态
普通算术/逻辑/跳转/访存可以（限本进程地址空间）可以
执行 I/O 指令、直接控制设备不可以可以
关中断/开中断、改中断向量不可以可以
修改 PSW 模式位、页表基址不可以可以
访问其他进程/内核的地址空间不可以（由 MMU 保护）可以（受内核自身约束）
执行陷入指令请求内核服务可以，这是合法入口可以（通常不需要再“陷入”）

注意“内核态”描述的是CPU 当前的特权级，不是“这段代码的地址一定在内核区”。同一段内核代码，如果被用户态以某种方式执行，它仍然受用户态限制；反过来，内核态可以执行普通指令，也可以访问用户地址空间（在受控前提下）。所以判断一道题里“CPU 处于什么态”，看的是当前 PSW 模式位和正在处理的事件，不是看进程名字。

四、特权指令与非特权指令

特权指令是只能在核心态执行的指令。它们的共同点是：一旦允许用户程序执行，就会破坏保护边界或改变全局机器状态。常见例子可以按“控制什么”来记：

类别典型指令/操作为什么必须特权
I/O 控制启动/停止设备、IN/OUT、清除设备状态绕过文件系统和设备权限，直接读写外设
中断控制关中断、开中断、设置中断屏蔽字、修改中断向量可以让系统失去抢占能力，或把中断导向恶意代码
处理器状态修改 PSW 模式位、设置优先级、停机、复位直接提升权限或让整机停止
存储管理修改页表基址、段表基址、MMU 控制寄存器、刷新 TLB可以映射/篡改任意物理内存
时钟/定时设置系统时钟、定时器、看门狗影响调度、超时和安全
控制寄存器/微程序写控制寄存器、加载微程序、切换地址空间直接改变 CPU 的工作方式

非特权指令是用户态可以执行的普通指令：算术运算、逻辑运算、移位、比较、条件转移、对自身地址空间的 load/store、压栈出栈、过程调用等。它们不会直接改变全局机器状态；如果访问了不该访问的地址，由 MMU 在访存时触发异常，而不是由“指令本身”越权。

最容易被误判的是陷入指令（trap、syscall、访管指令）。它是用户态可以执行的：如果它也是特权指令，用户程序就永远无法主动请求操作系统服务。陷入指令的作用不是“执行内核操作”，而是“产生一个受控的异常，让硬件把 CPU 切换到内核态，跳到内核预先登记的处理程序”。真正执行服务的是内核态的系统调用服务例程，不是用户态的那条 trap 指令。

因此要区分三个层次：

  • 系统调用：用户程序看到的功能接口，例如 read、write、fork；
  • 陷入指令：用户态真正执行的机器指令，例如 x86 的 int 0x80/syscall、RISC-V 的 ecall；
  • 系统调用服务例程：内核态运行的实现代码。

把“系统调用”说成“特权指令”是错的；把“陷入指令”说成“内核态指令”也不准确——它由用户态执行，执行后 CPU 才进入内核态。

五、模式切换的通道

用户态不能直接跳到内核态，必须经过硬件认可的“门”。硬件事件分两类：中断（异步）和异常（同步）；系统调用则利用异常中的陷入（trap）主动进入内核。它们都会让 CPU 保存当前 PSW/PC，切换到内核态，并跳到相应的处理程序。

内核态内部再发生中断/异常，仍是内核态，只是嵌套；用户态执行普通指令也不会换模式。这两条“同态内”的路径没有画进图里，避免把状态图画成一团。

一次典型的“用户态 → 内核态”切换，硬件大致做这些事：

  1. 保存被中断指令的断点（PC）和当前 PSW；有的机器保存到内核栈，有的用影子寄存器/专用寄存器；
  2. 把 CPU 模式位改成内核态；
  3. 根据中断/异常类型取得处理程序入口（中断向量/异常向量）；
  4. 跳到处理程序，由软件保存通用寄存器等现场，再处理事件。

返回时执行中断/异常返回指令（IRET、ERET、sysexit 等），从栈中恢复 PSW 和 PC；如果返回到用户程序，模式位随之恢复成用户态，CPU 回到断点继续执行。注意：模式位的改变是硬件在进入/返回时完成的，不是用户程序自己写的。

“中断、异常、陷入”三者的区别可以先用一张表建立框架，具体的中断响应、向量、嵌套在 I/O 与中断章节再展开：

事件来源同步性典型例子返回行为
外部中断CPU 外部设备/时钟异步，可在两条指令之间发生I/O 完成、时钟中断、控制台输入返回下一条指令
故障 fault当前指令执行中发现错误同步缺页、除零、非法指令、地址越界修复后重新执行当前指令（或终止进程）
陷入 trap当前指令主动触发同步系统调用、断点、单步返回下一条指令
终止 abort硬件严重错误同步/不可恢复总线错误、硬件校验错通常不返回，终止进程或停机

这张表里最重要的是“返回哪条指令”：外部中断和陷阱返回下一条，故障返回当前这条重试。缺页就是典型：指令访问的页不在内存，硬件触发缺页异常，内核把页调进来、更新页表，再返回当前指令重新执行；如果返回下一条，这次访存就丢了。

还要注意：如果 CPU 已经在内核态，又发生中断/异常，它仍然是内核态，只是可能发生嵌套，不叫“用户态 → 内核态切换”。模式切换只在特权级真的改变时发生。

六、什么时候在用户态，什么时候在内核态

不要背“某个进程永远在内核态”这种说法。同一个进程会随着执行内容在两种状态之间来回切换；判断依据是当前正在执行哪段代码、处理什么事件。

场景典型状态说明
应用程序做算术、循环、访问自己的数组用户态普通指令，不涉及全局资源
用户库函数（如 memcpy、printf 的格式化部分）用户态库函数本身在用户空间；真正写设备时才陷入内核
Shell、编辑器、编译器、数据库服务器进程用户态它们也是用户程序，只是功能上像“系统软件”
系统调用包装函数刚执行陷入指令用户态 → 内核态包装函数在用户态；陷入后进入内核服务例程
系统调用服务例程、文件系统、设备驱动内核态需要访问内核数据结构、设备、页表
时钟中断、I/O 完成中断的处理程序内核态硬件切换后执行；处理完可能触发调度
缺页异常处理内核态选页框、读磁盘、改页表，然后返回重试
进程调度、上下文切换内核态要操作 PCB、运行队列、地址空间
内核初始化、引导内核态建立页表、中断向量、设备模型

几个容易混淆的点：

  • “系统调用”横跨两种状态：用户态执行陷入指令，内核态执行服务例程，返回时又回到用户态。问“系统调用在哪个态执行”要分清阶段。
  • “中断处理”一定在内核态：中断发生时硬件先切模式，再跳处理程序；处理程序不会在用户态运行。
  • “用户态程序不能访问内核地址”：这不是靠“约定”，而是页表/MMU 的保护位；越权访问会触发异常，由内核决定是否终止进程。
  • “内核态”不等于“进程在运行内核主程序”：进程可能只是通过系统调用短暂进入内核，处理完就返回；它仍然是同一个进程。

七、内核的支撑功能：时钟、中断、原语

操作系统内核通常被描述为“常驻内存、运行在内核态的核心部分”。它的功能可以分成两组：一组是支撑系统运转的基础设施，另一组是管理资源的业务功能。先看第一组：时钟管理、中断机制、原语。

1. 时钟管理

时钟管理不只是“显示当前时间”。内核依赖硬件定时器产生时钟中断，在每次中断里做这些事：

  • 维护系统时间、进程的 CPU 时间、时间戳；
  • 递减当前进程的时间片，决定是否触发调度；
  • 处理睡眠/定时等待、超时重传、看门狗；
  • 采样性能计数器、统计系统负载。

时钟中断是抢占式调度的心跳：没有它，一个死循环的用户程序可以永远占着 CPU，内核根本没有机会拿回控制权。时钟频率越高，时间片粒度越细、响应越及时，但中断开销也越大；这是一个典型的“精度 vs 开销”折中。

2. 中断机制

中断机制是内核的“神经”。它让 CPU 不必轮询设备，而能在事件发生时被硬件打断；它也是系统调用、缺页、除零等同步事件进入内核的通道。内核需要准备：

  • 中断向量/异常向量：每种事件对应的处理程序入口；
  • 优先级与屏蔽：哪些中断可以嵌套、哪些必须延迟；
  • 现场保存与恢复：保存寄存器、PSW、PC，返回时恢复；
  • 中断服务程序：处理设备、唤醒进程、触发调度。

“中断机制是内核基本功能”这句话的含义是：没有它，内核既不能响应外部事件，也不能从用户态收回 CPU，更不能实现系统调用和异常处理。它不只是“I/O 完成通知”，而是整个 OS 运行模型的底座。

3. 原语

原语是由若干条指令组成、必须原子完成的操作：要么全部做完，要么一条都没做，中间不能被其他进程打断。典型例子包括进程的创建/撤销、阻塞/唤醒、信号量的 P/V、加锁/解锁、就绪队列的插入/删除。

为什么需要原子性？以“唤醒一个等待进程”为例：内核要修改进程状态、把它从等待队列移到就绪队列、可能还要设置调度标志。如果这些步骤中间被中断，另一个进程可能看到“状态已改但队列没移”的半成品，系统就乱了。原语把这些步骤包成一个不可分割的整体。

在单处理机上，原语常用关中断/开中断实现：关中断后，当前 CPU 不会被中断打断，关键几步就能连续完成；完成后开中断。但关中断只能阻止本 CPU 响应中断，多处理机上其他 CPU 仍在并发访问共享数据，所以还要配合原子指令（Test-and-Set、Compare-and-Swap、LL/SC 等）和内存屏障。原语运行在内核态，用户程序不能直接执行“关中断”来实现自己的原子操作；用户看到的互斥锁、信号量，最终由内核的系统调用或原子指令支撑。

八、内核的资源管理功能

支撑功能让内核“能运行”，资源管理让内核“把资源分好”。经典的四项是进程管理、存储器管理、文件管理、设备管理。

管理对象内核要解决的问题关键数据结构/机制
进程管理谁可以运行、何时运行、如何同步与通信PCB、进程状态、调度队列、上下文、信号量/管程
存储器管理内存怎么分、地址怎么转、如何保护与共享页表/段表、页框分配、虚拟存储、TLB、缺页处理
文件管理文件如何组织、目录如何查、空间如何分配FCB/inode、目录项、位图/空闲链表、访问控制
设备管理设备如何驱动、I/O 如何缓冲与调度设备控制块、驱动程序、缓冲区、SPOOLing、中断/DMA

这四项不是并列的“模块清单”，它们之间有很强的依赖：进程管理要调用存储器管理切换地址空间；文件管理最终要通过设备管理读磁盘；设备中断又要唤醒等待 I/O 的进程，回到进程管理。把这条链走一遍，比孤立背四个名字更有用。

还要注意“内核功能”的边界不是绝对的。宏内核（monolithic kernel）把文件系统、设备驱动、网络协议栈都放在内核态；微内核（microkernel）只把时钟、中断、低级存储管理、进程间通信等最基本的功能留在内核，文件系统和驱动移到用户态服务进程。408 默认讨论的是通用宏内核结构，但遇到“微内核”概念时，要知道“内核态运行的不一定都是内核代码”这个边界。

九、模式切换不等于进程切换

这是选择题里非常容易被偷换的一对概念。

对比模式切换进程切换
改变什么CPU 特权级（用户态 ↔ 内核态）当前运行的进程（PCB、地址空间、寄存器现场）
是否换地址空间不换通常要换页表基址，可能刷新 TLB
触发者中断、异常、陷入、返回指令调度器决定换另一个进程
开销保存/恢复 PSW、PC、部分寄存器，进入内核保存/恢复完整上下文，更新 PCB/队列，切换地址空间
典型例子一次只读系统调用：进内核取数据，马上返回时间片用完，调度到另一个进程

一次系统调用可能导致进程切换，但不是必然：如果请求的数据已经在缓存里，内核处理完就返回原进程，只有模式切换；如果请求磁盘 I/O，原进程被阻塞，调度器才会切换到另一个进程，这才发生进程切换。把“系统调用 = 进程切换”当成必然，是另一个常见错误。

模式切换本身的开销主要是保存/恢复现场、切换内核栈、可能污染 Cache；进程切换还要加上地址空间切换、TLB 失效、调度器开销，通常更贵。这也是为什么系统调用要尽量少做、批量做，为什么时间片不能太小。

十、易错点与收束

  • “系统调用是特权指令”：系统调用是接口；陷入指令由用户态执行；服务例程在内核态运行。
  • “用户态可以改 PSW 进入内核态”：模式位是受保护状态，用户只能通过中断/异常/陷入让硬件切换。
  • “在内核态执行的一定是内核代码”：内核态是 CPU 特权级；中断处理、系统调用服务都在内核态，但微内核中部分服务可以在用户态。
  • “模式切换就是进程切换”：模式切换只换特权级；进程切换还要换 PCB、地址空间和完整现场。
  • “中断只来自 I/O”：时钟、控制台、异常、系统调用陷入都会进入内核；中断机制是 OS 的通用入口。
  • “原语就是一条指令”：原语可以由多条指令组成，关键是原子性；单处理机靠关中断，多处理机还要原子指令。

把这一节收成一条链：PSW 模式位定义当前特权级 → 特权指令只在核心态执行 → 用户通过中断/异常/陷入进入内核 → 内核用时钟、中断、原语维持运转 → 用进程、存储、文件、设备管理资源 → 返回用户态继续执行。后面所有“谁在什么时候能做什么”的问题，都可以回到这条链上判断。
