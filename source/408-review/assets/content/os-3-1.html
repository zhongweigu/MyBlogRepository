PV 题看起来是“写几个 P、几个 V”，真正的难点是先把题目翻成并发约束。信号量只是一个整数计数器 + 等待队列；P 是“我要满足条件/拿资源”，V 是“我让条件成立/还资源”。把互斥、资源数量限制、同步这三类关系分清，代码只是把关系落到 P/V 上。

一、PV 到底在解决什么

并发进程之间只有三类约束：

约束题目里的说法信号量初值
互斥同一个资源/变量/缓冲区，同一时刻只能一个人用mutex1
资源数量限制最多 N 个进程同时做某件事，或有 N 个名额/座位/设备resourceN
同步A 做完以后 B 才能做；先生产后消费sync0

互斥是“不能同时”，资源限制是“最多几个”，同步是“谁先谁后”。这三类可以叠加：生产者-消费者就是“同步 + 互斥”，读者-写者是“角色不对称的互斥”，哲学家是“多个资源组合申请”。

二、信号量的结构与 P/V 语义

一个记录型信号量可以看成：

typedef struct {
    int value;          // 可用资源数；负数绝对值 = 等待进程数
    Queue queue;        // 阻塞在该信号量上的进程队列
} semaphore;

void P(semaphore S) {   // wait / 申请
    S.value--;
    if (S.value < 0) block(S.queue);
}

void V(semaphore S) {   // signal / 释放
    S.value++;
    if (S.value <= 0) wakeup(S.queue);
}
  • value >= 0：还有多少可用资源/名额；
  • value < 0：没有资源，绝对值是等待队列长度；
  • P 可能阻塞，V 可能唤醒；P/V 必须原子执行。

P 的“减一”不是简单的计数：它先占用一个资源，若占用后变负，说明资源已经不够，当前进程要睡眠。V 的“加一”也不是简单归还：若加完仍 ≤0，说明有人在等，要唤醒一个。

同一个 P/V 在不同场景下语义不同：互斥/资源场景是“拿/还”，同步场景是“等/通知”。不要把“P 就是加锁”背死。

三、互斥模型

临界资源一次只允许一个进程访问，初值 mutex=1：

semaphore mutex = 1;

P1() {
    while (1) {
        P(mutex);
        临界区;          // 访问共享变量/缓冲区/设备
        V(mutex);
        剩余区;
    }
}

P2() {
    while (1) {
        P(mutex);
        临界区;
        V(mutex);
        剩余区;
    }
}

第一个进程 P 后 value 从 1 变 0，进入临界区；第二个进程 P 后变 -1，阻塞。第一个进程 V 后 value 回到 0，唤醒第二个。互斥成立，且阻塞等待满足让权等待。

P/V 必须成对，且 V 要放在所有退出路径上；临界区内不能有“永远不返回”的路径，否则锁永远不释放。

四、资源数量限制

有 N 个相同资源/名额，初值 resource=N：

semaphore resource = N;

process() {
    while (1) {
        P(resource);     // 申请一个名额
        使用资源;
        V(resource);     // 归还名额
    }
}

前 N 个进程可以直接通过，第 N+1 个开始阻塞；每释放一个名额，唤醒一个等待者。互斥是 N=1 的特例：mutex 就是“只有一个名额的资源信号量”。

题目说“最多 4 人同时进餐”“最多 3 个进程读”“有 5 台设备”时，优先想到资源信号量，而不是给每个人再加一把互斥锁。

五、同步模型

A 完成后 B 才能做，初值 sync=0：

semaphore sync = 0;

A() {
    操作A;
    V(sync);             // 通知：A 已经完成
}

B() {
    P(sync);             // 等待：A 完成的通知
    操作B;
}

如果 B 先执行，P 后 value 变 -1，B 阻塞；A 执行 V 后 value 回到 0，唤醒 B。如果 A 先执行，V 后 value 变 1，B 再 P 时 value 变 0，不阻塞——信号量“记住”了这次通知。

同步信号量初值为什么是 0？因为“事件还没发生”。设成 1 等于告诉后继进程“已经发生过”，B 会直接通过，顺序就被破坏。

六、P/V 的顺序与死锁

当一个进程需要多个信号量时，P 的顺序可能造成死锁。典型反例：

// 错误：两个进程以相反顺序申请
P1: P(S1); P(S2);
P2: P(S2); P(S1);

P1 拿到 S1、P2 拿到 S2，双方再等对方，形成循环等待。解决方法是所有进程按同一顺序申请，或把多个资源合并成一个资源信号量。

生产者-消费者里的“先 P(empty) 再 P(mutex)”也是顺序问题：如果先拿 mutex 再等 empty，缓冲区满时生产者会拿着锁睡眠，消费者无法进入，死锁。一般原则：先 P 同步/资源，再 P 互斥；V 先释放互斥，再通知。

七、五步法

  1. 找关系：列出谁和谁互斥、最多几个、谁必须先于谁。
  2. 定类型：一个临界资源 → mutex；N 个名额 → resource；A 先于 B → sync。
  3. 设初值：mutex=1，resource=N，sync=0；读者-写者另有 count=0、rw=1、count 的保护 mutex=1。
  4. 落代码：互斥夹住临界区；同步“前驱 V、后继 P”；资源“用时 P、用完 V”。
  5. 检查：每个进程是否覆盖、P/V 是否成对、P 顺序是否可能循环等待、计数是否超过资源数。
题目信号优先判断初值
“同一时刻只能一个”互斥1
“最多 N 个”/“N 个资源”资源数量限制N
“A 完成后 B 才能”同步0
“读者可以同时，写者不能”角色矩阵 + countrw=1, mutex=1, count=0
“每人需要两个资源”多资源组合 + 死锁chopsticks=1，另加限制

八、检查清单与收束

  • 初值：同步量是不是 0？资源量是不是 N？empty/full 有没有互换？
  • P 顺序：有没有拿着 mutex 去等同步量/资源？多个信号量是否按同一顺序？
  • V 配对：每个 P 是否都有 V？异常/退出路径是否释放？
  • 覆盖：每个生产者/消费者/读者/写者进程都写了吗？只写一个进程会漏分。
  • 死锁/饥饿：多个资源是否形成环？读者优先是否饿死写者？

把这一节收成一句话：PV 不是代码模板，而是把“互斥、资源、同步”翻译成信号量；先关系、后初值、再代码、最后按交错检查。
