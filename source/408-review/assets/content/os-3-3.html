读者-写者不是“所有人抢一把锁”。它考的是角色不对称：读者之间可以同时读，读者和写者不能同时，写者和写者也不能同时。做这道题，先画“谁可以和谁同时”的矩阵，再决定谁和谁互斥。

一句话总结：写者正常申请和释放“写”，读用 count 记录在读的读者数量；如果是第一个读者就阻止写，如果是最后一个读者就释放写。写者优先就是再给写者加一个高优先的互斥量，后来的读者会被这个信号量阻止。

一、四条规则与角色矩阵

读者-写者问题的经典要求：

  1. 允许多个读者同时对文件读；
  2. 只允许一个写者写；
  3. 写者写时，不允许其他读者或写者工作；
  4. 写者开始写之前，已有读者和写者都要退出。
角色组合能否同时原因
读者 + 读者可以读不改变数据，可以共享
读者 + 写者不可以写会改变数据，读可能读到不一致
写者 + 写者不可以两个写会互相覆盖

所以不是“共享文件 → 所有人互斥”，而是“写者与所有人互斥，读者之间放行”。这就是读者-写者的核心。

二、把读者看成一个整体

把“所有读者”当成一个整体，让它和写者互斥：

  • 第一个读者到达时，代表读者整体去抢 rw，把写者挡住；
  • 后续读者不需要再抢 rw，直接加入读；
  • 最后一个读者离开时，代表读者整体释放 rw，放写者进来。

因此需要两个东西：rw（读者整体/写者的互斥）和 count（当前读者数）。count 是普通整数，不是信号量——它不需要排队，也不限制读者上限；但多个读者同时修改它，必须用 mutex 保护。

三、读者优先代码

semaphore rw = 1;      // 写者与“读者整体”互斥
semaphore mutex = 1;   // 保护 count
int count = 0;         // 当前读者数

writer() {
    while (1) {
        P(rw);
        写文件;
        V(rw);
    }
}

reader() {
    while (1) {
        P(mutex);
        if (count == 0) P(rw);  // 第一个读者挡住写者
        count++;
        V(mutex);

        读文件;

        P(mutex);
        count--;
        if (count == 0) V(rw);  // 最后一个读者放行写者
        V(mutex);
    }
}

走一遍：第一个读者 count=0，执行 P(rw) 拿到文件；第二个读者看到 count=1，不再 P(rw)，直接读。写者此时 P(rw) 会阻塞。最后一个读者 count 减到 0，V(rw)，写者被唤醒。

四、count 为什么还要 mutex

读者虽然只读文件，但他们会修改 count。对 count 来说，每个读者都是“写者”：两个读者同时执行 count++，可能都读到旧值 0，最后 count 只加了一次。于是：

  • 第一个读者可能重复 P(rw)（如果都以为自己是第一个）；
  • 最后一个读者可能提前 V(rw)，写者与读者并发；
  • 读者数量错误，导致 rw 永远不释放或提前释放。

所以 count 的“读—改—写”必须放在 P(mutex)/V(mutex) 内。注意 mutex 只保护 count，不保护整个读文件过程；读操作本身可以并发。

五、写者饥饿与 w 信号量

上面的代码是读者优先：只要还有读者在，写者就得等；读者不断到达时，写者可能永远进不去，发生写者饥饿。

要让写者相对公平，增加一个入口信号量 w=1：读者和写者进入前都先 P(w)，离开入口时 V(w)；这样写者排队后，后来的读者不能不断插队。

semaphore rw = 1;
semaphore mutex = 1;
semaphore w = 1;       // 入口排队，缓解写者饥饿
int count = 0;

writer() {
    while (1) {
        P(w);
        P(rw);
        写文件;
        V(rw);
        V(w);
    }
}

reader() {
    while (1) {
        P(w);
        P(mutex);
        if (count == 0) P(rw);
        count++;
        V(mutex);
        V(w);           // 进入读者整体后立刻释放入口

        读文件;

        P(mutex);
        count--;
        if (count == 0) V(rw);
        V(mutex);
    }
}

写者等待时持有 w，后续读者在 P(w) 处排队，不能继续插队；已在读的读者读完后，最后一个释放 rw，写者进入。反过来，如果写者持续到达，读者也可能被挡在 w 外——所以这是“相对公平/写者优先”，不是绝对公平。

六、读者优先/写者优先/公平

策略做法风险
读者优先只有第一个读者 P(rw)，后续读者直接加入写者可能饥饿
写者优先/相对公平入口加 w，写者等待时挡住新读者持续写者可能让读者等待
严格公平按到达顺序排队（如 FIFO 信号量/票据锁）实现复杂，并发度可能下降

考试里如果题目没有特别要求“公平”，通常写读者优先版即可；如果题目明确“写者不被饿死”或“写者优先”，再加 w。不要默认加 w 就一定更好，它会改变读者/写者的相对优先级。

七、易错点与收束

  • “count 是信号量”：count 是计数变量，不需要排队；保护它的是 mutex。
  • “每个读者都 P(rw)”：只有第一个读者 P(rw)，否则读者之间也互斥，失去并发。
  • “最后一个读者不 V(rw)”：写者会永远等不到文件。
  • “count++ 不用保护”：多个读者同时改 count 会丢更新，可能导致 rw 提前/延迟释放。
  • “加 w 绝对公平”：w 只是入口排队；持续写者仍可能让读者等待。

把这一节收成一句话：rw 管“读者整体 vs 写者”，mutex 管 count，count 管“第一个/最后一个读者”；w 只是可选的公平入口。
