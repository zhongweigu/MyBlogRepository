进程既是资源分配单位，又是调度单位。但一个进程里如果只有一条执行流，它一旦阻塞，整个进程就停住；创建/切换进程又要换地址空间，代价高。线程把这两件事拆开：资源仍然归进程，CPU 调度交给线程。理解线程，重点不是“线程更轻”，而是看清哪些资源共享、哪些私有、谁来调度。

一、为什么需要线程

如果进程既是资源单位又是调度单位，会有两个问题：

  • 切换贵：进程切换要换页表、刷新 TLB、保存完整现场；
  • 并发粒度粗：一个进程只有一个执行流，进程内某段代码阻塞，整个进程都停。

线程把“执行流”从进程里拆出来：同一进程可以有多个线程，它们共享地址空间和打开文件，但各自有寄存器、PC、栈和 TCB。这样，一个线程等待 I/O 时，另一个线程还可以继续跑；线程切换通常不用换地址空间，开销比进程切换小。

但“轻”不是免费的：线程共享地址空间，任何线程都能读写其他线程的栈和全局变量，数据竞争和同步问题比进程更直接。

二、进程与线程的分工

维度进程线程
定位资源分配的基本单位调度/分派的基本单位
地址空间独立同一进程内共享
拥有资源地址空间、文件、设备等基本不拥有资源，依附于进程
私有内容PCB、页表、地址空间寄存器、PC、栈、TCB
切换开销较大，可能换页表/TLB较小，同进程内通常不换页表
通信需要共享存储/消息/管道直接读写共享变量（需同步）
健壮性进程间隔离较好一个线程崩溃可能拖垮整个进程

所以“线程是轻量级进程”这个说法只对了一半：它轻在切换和资源共享，但代价是隔离性变差。

三、共享什么，私有什么

共享私有
代码段、数据段、堆寄存器现场（通用寄存器、PC、PSW）
打开的文件、当前目录用户栈和内核栈
信号处理函数、地址空间线程 ID、TCB、优先级/调度信息
进程的资源和权限线程局部存储（TLS）

“共享堆、私有栈”意味着：一个线程 malloc 出来的内存，其他线程可以直接访问；但一个线程的局部变量在它自己的栈上，其他线程要拿到地址才能访问——而语言/运行时通常不鼓励这样。线程之间没有 MMU 保护，栈溢出或野指针可能破坏其他线程的数据。

四、ULT：用户级线程

ULT（User-Level Thread）把线程的创建、切换、调度都放在用户空间的线程库里，内核只看到一个普通的单线程进程。线程库维护线程表和 TCB，切换时保存/恢复用户寄存器，不需要陷入内核。

优点：

  • 线程切换不需要模式切换，开销小；
  • 进程可以为自己的线程选择专用调度算法；
  • 线程库在用户空间实现，可移植，甚至能在不支持线程的 OS 上运行。

缺点：

  • 内核只识别进程，每次只能把一个 CPU 分给整个进程；同一进程的多个 ULT 无法在多核上真正并行；
  • 一个 ULT 发起阻塞系统调用（如 read）时，内核会阻塞整个进程，其他 ULT 也跑不了；
  • 内核级事件（时钟、I/O）只能打断进程，线程库再决定切换哪个线程。

五、KLT：内核级线程

KLT（Kernel-Level Thread）由内核直接管理：每个线程有内核中的 TCB，内核调度器直接调度线程。用户线程通过系统调用创建/销毁内核线程，线程切换要进入内核。

优点：

  • 多核/多处理机上，同一进程的多个线程可以分到不同 CPU，真正并行；
  • 一个线程阻塞时，内核可以调度同进程其他线程，或调度其他进程；
  • 内核可以直接利用时钟中断做抢占式线程调度。

缺点：

  • 线程切换要进内核，模式切换和调度开销更大；
  • TCB 放在内核空间，占内核内存；
  • 线程创建/销毁/同步更多依赖系统调用。

六、多线程模型

模型用户线程 : 内核线程特点
多对一多个 ULT → 一个 KLT接近 ULT；切换快，但一个阻塞全阻塞，不能多核并行
一对一一个 ULT → 一个 KLT并发/并行好，但线程创建和切换开销大，内核线程数量受限
多对多多个 ULT → 多个 KLT复用内核线程，兼顾并行和开销；实现复杂

很多系统还会用“两层模型”：既有多对多，也允许某些线程绑定到专用内核线程。模型的选择本质上是并行度、切换开销、内核资源三者的折中。

七、线程实体：TCB、栈与“线程映像”

线程没有“像进程映像那样的一整套独立地址空间”。它寄生在进程的地址空间里：代码段、数据段、堆、共享库都复用进程的；线程自己需要的是执行上下文——寄存器、PC、栈指针、栈、TCB，以及线程局部存储（TLS）。

组成放在哪作用
TCB（线程控制块）ULT 在用户空间线程库；KLT 在内核空间线程 ID、状态、寄存器现场、栈指针、优先级、等待事件、链接指针
用户栈进程的用户地址空间函数调用、局部变量、返回地址；每个线程独立
内核栈内核空间（KLT 必需）线程进入内核/中断时保存现场，不能和用户栈混用
TLS进程地址空间中的线程局部区每个线程一份的全局/静态变量，如 errno、线程私有缓存
寄存器现场切换时保存到 TCB/内核栈通用寄存器、PC、PSW、SP、浮点/SIMD 状态

所以“线程映像”如果非要类比，只能说它是线程执行上下文 + 私有栈 + TCB，不含独立的代码/数据/页表。线程切换保存的是这套上下文；同一进程的线程切换通常不换页表，因此比进程切换轻。进程切换则要换地址空间（页表基址、TLB），并保存/恢复 PCB。

线程的栈也不能和进程的“用户栈”混为一谈：进程映像里画的那段用户栈，是多线程进程里主线程的栈；其他线程各自有栈，通常由线程库在堆/匿名映射区分配。KLT 还要为每个线程准备内核栈。

八、KLT 里为什么还有用户级线程

“内核级线程”说的是内核能识别、能直接调度的实体；“用户级线程”说的是应用程序看到的线程对象/线程库。两者不是互斥的层次，而是“用户态的管理对象”和“内核里的调度实体”之间的映射关系。

  • 一对一模型中，程序员用 pthread 创建一个用户线程，线程库再通过 clone 等系统调用创建一个内核线程；用户线程是句柄，内核线程是调度单位。内核看到的是 KLT，但用户程序仍然在创建/管理用户级线程。
  • 多对多模型中，多个用户线程复用少量内核线程；线程库负责在用户态切换，内核只调度内核线程。这时既有 ULT 的灵活性，又有 KLT 的并行能力。
  • 即使是一对一，线程库仍要管理用户栈、TLS、线程创建/销毁、同步对象；这些是用户态职责，不能因为“内核能看到线程”就消失。

所以“KLT 里还有用户级线程”不是矛盾：KLT 是内核的调度对象，ULT 是用户程序的并发抽象；一个 KLT 可以承载一个或多个 ULT，具体看模型。

九、延伸：pthreads、Linux clone 与常见实现

POSIX 线程（pthreads）是应用编程接口，不是实现。Linux 的 NPTL 采用一对一模型：每个 pthread 对应一个内核调度实体；底层用 clone 创建，传入 CLONE_VM（共享地址空间）、CLONE_FS（共享文件系统信息）、CLONE_FILES（共享文件描述符表）、CLONE_SIGHAND（共享信号处理）等标志，于是新实体与父实体共享资源，但有自己的寄存器/栈，成为“线程”。

Windows 的线程由内核对象表示，内核直接调度；Java 的线程在主流 JVM 上通常映射到 OS 线程；Go 的 goroutine 是运行时管理的 M:N 用户态调度，多个 goroutine 复用到若干 OS 线程。这些例子说明：“线程”既可以是语言/库的概念，也可以是内核的调度实体，关键是看谁创建、谁调度、共享什么。

外部资料可以重点看三处：pthreads 的线程创建/join、Linux `clone` 的标志位、以及 Go scheduler 的 G-M-P 模型。它们分别对应“用户接口”“内核实现”“M:N 调度”三个层次。

十、切换、同步与易错点

线程切换保存/恢复寄存器、PC、SP 和 TCB；同一进程的线程共享页表，所以通常不换地址空间、不刷新 TLB。进程切换则可能换页表，代价更高。

线程共享地址空间，必须用互斥锁、信号量、条件变量等保护共享数据。一个线程打开的文件，其他线程也能读写；这也意味着“线程安全”不是自动的。

  • “线程有独立地址空间”：同一进程的线程共享地址空间；只有进程之间独立。
  • “ULT 切换一定要进内核”：ULT 的线程切换由用户库完成，不需要模式切换。
  • “ULT 一个线程阻塞不影响其他线程”：ULT 的阻塞系统调用会让整个进程阻塞。
  • “KLT 没有开销”：KLT 切换要进内核，TCB 也占内核资源。
  • “线程越多越好”：线程创建/切换/同步都有开销，还会争用 CPU、Cache 和内存。

把这一节收成一句话：进程管资源，线程管执行；ULT 在用户空间调度、快但怕阻塞，KLT 在内核调度、能并行但有切换开销。
