用户代码里写一句 read(fd, buf, n)，看起来像调用了一个普通函数，实际上它可能跨越了用户态和内核态之间最硬的一条边界。理解系统调用，关键不是背“有哪些函数”，而是看清三件事：谁在用户态准备参数、哪条指令真正陷入内核、内核又怎样把结果送回来。

一、系统调用不是普通函数调用

普通函数调用发生在同一个特权级里：调用者和被调用者都在用户态，CPU 不换模式，只是把返回地址压栈、跳到函数入口。系统调用不同：用户程序要让内核替它做一件自己无权做的事，必须主动触发一次受控的异常，让 CPU 切换到内核态。

为什么不能直接调用内核函数？因为内核函数运行在内核态，能改页表、关中断、访问设备。如果用户程序能任意跳进内核函数，保护边界就形同虚设。所以操作系统只暴露一组固定入口：用户程序把“要什么服务、参数是什么”放进约定好的寄存器，执行一条陷入指令；CPU 按硬件约定跳到内核入口，内核再根据编号分发。

对比普通函数调用系统调用
特权级不变，仍在用户态用户态 → 内核态 → 用户态
入口编译器/链接器确定的函数地址硬件异常/陷入入口，再由内核查表分发
参数传递栈或寄存器，调用约定ABI 约定的寄存器（x86-64：rdi/rsi/rdx…）
能否被抢占/阻塞普通函数一般不主动阻塞内核服务可能睡眠、等待 I/O、触发调度
开销压栈、跳转、返回模式切换、现场保存、参数校验、数据拷贝

所以“系统调用”是接口，不是一条具体的机器指令。用户程序看到的是 read、write、fork 这些函数；真正让 CPU 跨边界的是函数内部的陷入指令。

二、从 read() 到 syscall：用户态做了什么

下面以 x86-64 Linux 的 read(fd, buf, nbytes) 为例。用户代码调用的是 C 库里的 read()，它通常是一个很薄的包装函数：

  1. 准备参数：文件描述符 fd 放入 rdi，缓冲区地址 buf 放入 rsi，字节数 nbytes 放入 rdx；
  2. 放系统调用号：Linux x86-64 上 read 的编号是 0，放入 rax；
  3. 执行陷入指令：syscall 让 CPU 进入内核；
  4. 取返回值：内核把读到的字节数或负错误码放回 rax；库函数再按需设置 errno。

三、把示例代码逐行拆开

下面是一段简化后的原始系统调用写法，方便看清寄存器约定；实际 C 库的 read() 还会处理取消点、errno、符号版本等细节，但跨边界的那一步不变。

; x86-64 Linux：read(fd, buf, nbytes) 的简化写法
mov rdi, fd        ; 第 1 个参数：文件描述符
mov rsi, buf       ; 第 2 个参数：用户缓冲区地址
mov rdx, nbytes    ; 第 3 个参数：最多读多少字节
mov rax, 0         ; read 的系统调用号（Linux x86-64）
syscall            ; 触发系统调用，进入内核
; 返回值在 rax：
;   >= 0：实际读到的字节数（0 表示 EOF）
;   < 0：负错误码，例如 -EFAULT、-EBADF
mov [nread], rax   ; 把返回值保存到用户变量
寄存器本例中的用途说明
rax系统调用号 / 返回值调用前放 0；返回后放字节数或负错误码
rdi第 1 个参数文件描述符 fd
rsi第 2 个参数用户缓冲区地址 buf
rdx第 3 个参数要读取的字节数 nbytes
rcx / r11被 syscall 使用分别保存返回 RIP 和 RFLAGS；用户代码不要依赖它们的原值

这张表只对 x86-64 Linux 成立；换架构、换操作系统，系统调用号、参数寄存器和陷入指令都会变。408 不会要求背具体编号，但会考“参数/编号放哪、哪条指令陷入、返回值在哪”这类机制。

四、内核入口、分发与返回

CPU 执行 syscall 后，硬件会完成一次受控的异常进入：保存返回地址和标志、切换栈、跳到内核预先登记的入口。内核入口再做这些事：

  1. 保存现场：把用户寄存器、栈指针等保存到内核栈或进程的上下文结构；
  2. 按编号分发：用 rax 作为索引查系统调用表，得到 sys_read 等服务例程的入口；
  3. 校验参数：检查 fd 是否合法、buf 是否在用户地址空间、长度是否越界；用户指针不能直接解引用；
  4. 执行服务：读文件/设备、拷贝数据；如果需要等待 I/O，当前进程可能睡眠，调度器切换到别的进程；
  5. 返回：把结果写入 rax，恢复现场，执行 sysret（或 iret）回到用户态。

这里有两个“切换”要分清：模式切换是 CPU 从用户态到内核态，几乎每次系统调用都会发生；进程切换是内核决定换另一个进程运行，只有服务阻塞或时间片到期等情况下才发生。一次只读缓存数据的 read 可能只有模式切换，没有进程切换。

返回时，内核把结果放在 rax。原始系统调用用负值表示错误（Linux 常见 -1 到 -4095）；C 库包装函数会把它翻译成“返回 -1，并设置 errno”。所以用户看到的是 read() == -1，而不是负数错误码，这两层不要混。

五、trap、int、syscall 与“软中断”

用户给的导图里写“系统调用本质就是中断”，这句话要分语境。严格说：系统调用通过“陷入/异常”进入内核，它是同步事件，不是外部设备中断。如果把“中断”广义地理解为“打断当前控制流、进入内核”，那它可以算一类；如果按 408 常说的“外部中断 vs 异常”，它属于异常中的 trap。

名称触发方式同步性典型例子是不是系统调用
外部中断设备/时钟发 IRQ异步，通常在指令边界响应键盘、磁盘完成、时钟不是
陷入 trap当前指令主动触发同步syscall、int 0x80、断点是（系统调用的入口）
故障 fault当前指令执行中出错同步缺页、除零、越界不是
终止 abort硬件严重错误同步/不可恢复总线错误、校验错不是
Linux softirq内核延迟处理机制由内核在合适时机执行网络收包的下半部不是

几个术语的关系可以这样记：

  • trap（自陷）：由指令主动触发、处理完返回下一条指令的同步异常；系统调用是典型 trap。
  • int：x86 的软件中断指令，例如 int 0x80；它也能从用户态进入内核，但现代 64 位系统更常用 syscall。
  • syscall：x86-64 的快速系统调用指令；它不等于“系统调用”这个抽象接口，只是入口指令。
  • 软中断：408 语境下常把 int/syscall 这类“由软件指令触发的中断”叫软中断；但 Linux 的 softirq 是内核延后处理机制，和系统调用不是一回事。

所以更准确的说法是：系统调用是用户程序请求内核服务的接口；它通过陷入指令以同步异常的方式进入内核。不要把它说成“设备中断”，也不要把 Linux 的 softirq 当成系统调用的实现。

六、系统调用、库函数与 API 的边界

“系统调用”经常被和“库函数”“API”混着说。三者是不同层次：

层次例子是否一定进内核说明
C 库函数read、printf、memcpy不一定库函数可能完全在用户态完成，也可能内部调用系统调用
系统调用sys_read、sys_write、sys_fork是内核入口和实现，运行在内核态
编程接口/APIPOSIX、Win32 API不一定API 是规范；底层可能是一个或多个系统调用

例如 printf 通常先把格式化结果写进用户态缓冲区，缓冲区满或调用 fflush 时才执行 write 系统调用；memcpy 一般只是用户态的内存拷贝，不会进内核。反过来，read 在 C 库里是函数，但它内部确实会触发系统调用。判断时不要看“名字像不像系统调用”，要看它有没有跨特权级。

七、开销、错误与安全

系统调用比普通函数调用贵，原因不止“换了个模式”：

  • 模式切换：保存/恢复 PSW、PC、栈指针和部分寄存器，切换内核栈；
  • 参数校验：内核不能相信用户传来的指针、长度、fd，要检查合法性；
  • 数据拷贝：用户缓冲区与内核缓冲区之间可能要复制大量数据；
  • 可能的阻塞与调度：等待 I/O 时进程睡眠，触发进程切换。

所以高性能程序会尽量批量读写、减少小系统调用、用缓冲区合并操作；但优化不能以绕过保护为代价。内核侧则要用 copy_from_user/copy_to_user 一类机制安全搬运数据，防止用户指针非法、越界，或在中途被另一个线程改掉（TOCTOU 一类问题）。

“用户态发起”不意味着用户态能控制内核做什么：系统调用号决定入口，参数要经过内核校验，权限（文件属主、能力位、地址空间）仍由内核判断。用户只能请求，不能命令内核绕过规则。

八、常见误区与收束

  • “read() 就是系统调用指令”：read() 是库函数；真正跨边界的是它内部的 syscall/int 指令。
  • “系统调用就是外部中断”：系统调用是同步 trap，由指令主动触发；外部中断由设备异步触发。
  • “软中断就是系统调用”：408 的“软中断”常指软件中断指令；Linux softirq 是另一套内核机制。
  • “系统调用号就是服务程序地址”：编号只是系统调用表的索引，表项里才是入口。
  • “内核可以直接使用用户指针”：必须校验并安全拷贝，不能信任用户地址。
  • “系统调用一定导致进程切换”：不一定；只读缓存、快速服务可能只进出内核，仍回原进程。

把这一节收成一条链：用户调用库函数 → 参数/编号进寄存器 → 执行 syscall/int → CPU 陷入内核 → 查系统调用表 → 校验并执行服务 → sysret/iret 返回 → 库函数处理返回值。这条链把“用户态发起”“陷入”“内核服务”“返回”四件事串在了一起。
