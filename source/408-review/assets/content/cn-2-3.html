可靠传输要解决两个问题：帧丢了/错了怎么办，以及发送方发太快、接收方处理不过来怎么办。前者靠确认、超时和重传，后者靠流量控制/滑动窗口。停等、GBN、SR 是三种经典滑动窗口协议；窗口大小、序号位数和确认方式决定效率与复杂度。

先建立一个直觉：发送窗口 = 发送方“已发出但还没被确认”的帧集合；窗口越大，发送方能连续发越多帧，流水线越深。但序号只有 n 位，窗口不能无限大，否则新旧帧可能用同一个序号，接收端分不清“新帧”和“重传的旧帧”。

一、停等协议

发送方发一帧后停下，等待接收方的 ACK；超时未收到就重传。用 1 位序号（0/1）区分新帧和重复帧。

  • 正常：发 0 → 等 ACK0 → 发 1 → 等 ACK1；
  • 帧丢失/出错：超时重传；
  • ACK 丢失：发送方重传，接收方收到重复帧后丢弃并重发 ACK。

停等简单，但 RTT 大、速率高时信道利用率很低。可以把它想成“寄一封信，必须等回信才能寄下一封”：信件在路上的时间远大于写信时间，邮局大部分时间是空的。

停等还有两个细节：ACK 丢失时发送方会重传，接收方必须能识别重复帧；用 1 位序号 0/1 就够，因为“上一帧的 ACK”和“下一帧的数据”可以区分。若没有序号，接收方收到重复帧会误当成新数据。

二、GBN：回退 N

发送窗口 > 1，接收窗口 = 1。接收方只按序接收，用累积确认（ACK n 表示 n 及之前的帧都收到）。

  • 发送方可连续发多个帧，不必每帧都停；
  • 某帧超时，重传该帧及其后所有未确认帧；
  • 接收端遇到乱序帧直接丢弃，所以叫“回退 N”。
  • 序号 n 位时，发送窗口 ≤ 2^n − 1。

为什么是 2^n−1 而不是 2^n？如果窗口等于 2^n，发送方发完 0…2^n−1 后，ACK 全丢，又重发 0；接收方刚收完旧 0…2^n−1，无法判断新到的 0 是新帧还是旧帧的重传。留一个序号不用，接收方就能用“窗口位置”区分。

三、SR：选择重传

发送窗口和接收窗口都 > 1。接收方可以缓存乱序到达的帧，只重传出错/丢失的那一帧。

  • 逐帧确认，接收窗口内的乱序帧先缓存；
  • 缺失帧到达后，接收窗口向前滑动并交付；
  • 序号 n 位时，窗口 ≤ 2^(n−1)（发送/接收窗口通常相同）。

SR 效率高，但接收端缓存和排序逻辑更复杂。它适合误码率较高、RTT 较大、带宽时延积大的链路：如果每次出错都回退一大段，重传代价太高。

SR 的窗口为什么是 2^(n−1)？发送窗口和接收窗口加起来不能超过序号空间 2^n，否则新旧窗口会重叠；通常两边取一样大，于是各占一半。

四、窗口与信道利用率

停等协议的简化利用率：

U = T_D / (T_D + RTT + T_A)

其中 T_D 是发送一帧的时间，T_A 是 ACK 发送时间，RTT 是往返传播时延。RTT 越大，停等利用率越低。

代入一组数：帧长 1000bit，速率 1Mb/s，T_D=1ms；RTT=20ms，忽略 T_A。则 U=1/(1+20)≈4.76%。也就是说，链路只有不到 5% 的时间在发数据，其余都在等 ACK。若窗口能开到 21 帧，发送方在等 ACK 时继续发，U 才可能接近 100%。

滑动窗口相当于“流水线”：窗口足够大时，发送方在等待 ACK 期间还能继续发，利用率可接近 1。更准确地说，窗口至少要有“RTT 内能发出的帧数”那么多，才能把链路填满；这个帧数约等于 `(RTT × R)/L`，也就是带宽时延积除以帧长。

但窗口不能只按利用率开大：GBN 受 2^n−1 限制，SR 受 2^(n−1) 限制；序号位数不够时，必须降低窗口或增加序号位数。

五、易错点与收束

  • “GBN 接收窗口等于发送窗口”：GBN 接收窗口为 1，只按序接收。
  • “SR 不需要缓存”：SR 必须缓存乱序帧。
  • “窗口越大越好”：受序号空间限制，过大导致新旧帧混淆。
  • “停等不需要序号”：至少需要 1 位序号来识别重复帧。
  • “GBN 的累积确认表示所有帧都正确”：它表示到该序号为止都收到，但不代表后面没有出错。

收束：停等用时间换简单，GBN 用重传换秩序，SR 用缓存换效率；窗口大小由序号位数决定。
